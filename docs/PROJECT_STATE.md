## 1. Что за проект

Двумерная пиксельная игра на Go и ebiten (Ebitengine v2.10.4), вид сверху, похожа на Stardew Valley. Мир будет генерироваться процедурно по биомам, как в Minecraft. Позже мультиплеер (локальная сеть и/или интернет). Главная цель автора: **выучить Go, git и ebiten**, игра вторична.

- Модуль: `github.com/BikbaevR/game`, Go 1.26, IDE GoLand, ОС macOS.
- Репозиторий: https://github.com/BikbaevR/game (ветка `main`).
- Автор: `rafa`, русскоязычный. Общение, комментарии в коде и сообщения коммитов на русском.

## 2. Текущее состояние (кратко)

Работает: окно 640x480 показывает карту 20x15 из случайных тайлов (вода, трава, песок), по ней двигается белый квадрат-игрок клавишами WASD и стрелками. Движение плавное, в пикселях, диагональ нормализована. **Столкновений нет**: игрок ходит по воде.

Всё закоммичено и слито в `main`, рабочее дерево чистое (на 2026-10-06).

## 3. Структура проекта

```
cmd/game/main.go        — запуск: создаёт мир и игрока, настраивает окно, RunGame
internal/
  world/                — карта: Tile, TileType, TileInfo, Grid (БЕЗ ebiten)

  player/               — игрок и команда движения (БЕЗ ebiten)

  render/               — отрисовка (импортирует ebiten)

  game/                 — клиентская оболочка (ebiten): Game, ввод
```

### Зависимости пакетов (строго в одну сторону)

```
cmd/game → game → render → world
             ↓        ↓
             └→ player ←┘   (render импортирует player для DrawPlayer)
world    — не импортирует ничего из проекта
player   — не импортирует ничего из проекта
```

Пакеты `world` и `player` **не импортируют ebiten**: логика должна запускаться на сервере без графики. Ebiten используют только `render`, `game`, `main`.

## 4. Что реализовано

### `world`
- `TileSize = 16` (пикселей на тайл; лежит в `world`, потому что нужен логике; раньше был в `render`).
- `TileType uint8` с константами `TileWater=0`, `TileGrass=1`, `TileSand=2` (через `iota`).
- `TileInfo{Name, Walkable}` и таблица `tileInfos` (массив, индексируется `TileType`); `TileType.Info()`. Вода не проходима, трава и песок проходимы.
- `Tile{Type}` — клетка (позиция в клетке не хранится, её задаёт место в сетке).
- `Grid` — плоский срез `[]Tile`, индекс `y*width + x`. Методы: `NewGrid`, `Width`, `Height`, `InBounds`, `Get(x,y) (Tile, bool)`, `Set(x,y,Tile) bool`, приватный `index`.
- Тесты: `TestGrid_SetGet` (одна общая сетка, два цикла: запись, потом чтение), `TestGrid_OutOfBounds` (4 стороны по одному условию). Проверены мутациями.

### `player`
- `Size = 12` — сторона квадратного хитбокса в пикселях (меньше тайла).
- `ID uint32`, `Player{ID, Name, X, Y, Speed}`; `X, Y` — **центр** игрока в пикселях (`float64`); `Speed` — пикселей за тик.
- `New(id, name, x, y, speed)`.
- `MoveCommand{PlayerID, DX, DY}` — команда (намерение), `DX, DY` из -1, 0, 1.
- `(*Player).Apply(cmd)` — ранний выход при нулевом направлении (иначе NaN), нормализация вектора через `math.Sqrt`, сдвиг на `Speed`. Столкновения пока не учитываются.
- Тест `TestCommand_Apply` (табличный, 8 случаев, раздельные проверки X и Y). Проверен мутациями.

### `render`
- `tileColors` — массив `[...]color.RGBA` по `TileType` (цвет — забота отрисовки, не `world`).
- `DrawGrid(screen, grid)` — цветные квадраты через `vector.FillRect` (antialias=false).
- `DrawPlayer(screen, p)` — белый квадрат `player.Size`, нарисован вокруг центра `X, Y`.

### `game`
- `Game{world *world.Grid, player *player.Player}`, `New(w, p)`.
- `Update`: `readMoveCommand(id)` → `player.Apply(cmd)`.
- `Draw`: `DrawGrid`, затем `DrawPlayer`.
- `Layout`: размер считается из размеров мира `Width*TileSize x Height*TileSize` (сейчас 320x240).
- `input.go`: `readMoveCommand` читает WASD и стрелки через `ebiten.IsKeyPressed`. Использует `cmd.DY--` / `cmd.DY++`, поэтому противоположные клавиши гасят друг друга.

### `main`
- Окно 640x480, заголовок "Game". Сетка 20x15, заполняется `getRandomTile()` (один бросок `rand.Intn(3)`, равные вероятности). Игрок id=1, имя "test", скорость 1.2 пикселя за тик, спавн в центре карты. Константы `playerName`, `playerSpeed`.

## 5. Принятые решения и почему

- **Тайловый мир**, позиция игрока в **пикселях** (плавное движение, как в Stardew).
- **Тайл не хранит координаты**: их задаёт позиция в сетке (иначе дублирование и рассинхрон).
- **Вид тайла (`TileType`) отделён от клетки (`Tile`)**: описание вида одно на все клетки, в клетке только число (1 байт, легко слать по сети).
- **Сетка плоским срезом**: одна аллокация, данные подряд в памяти, проще сериализовать.
- **`world` не хранит игроков**: иначе цикл импортов `player ↔ world`. Мир и игрока держит `Game` (пока). Позже, при появлении сервера, держателя состояния выделить отдельно.
- **Команды вместо прямых вызовов из ввода**: `readMoveCommand` (знает ebiten) → `MoveCommand` (данные) → `Apply` (логика). Команда хранит *намерение* (направление), а не координаты: клиент не может телепортироваться. Нормализация делается в логике, чтобы клиент не мог ускориться большими числами.
- **Скорость в пикселях за тик**: `Update` вызывается фиксированно 60 раз в секунду, поведение детерминировано.
- **Никаких `Controller`/`Manager` объектов** («player controller» из Unity): ввод и логика разделены по пакетам.
- **`TileSize` в `world`**, размер хитбокса игрока в `player`: логика не зависит от `render`.
- **Позиция игрока — центр**, хитбокс 12x12 меньше тайла.
- **Id игрока — число (`uint32`)**, а не UUID: короче в сети, нет внешней зависимости. Имя не идентификатор.
- Размер мира (бесконечный по чанкам или конечный) **ещё не выбран**.

## 6. Соглашения

- Ось Y направлена вниз; «вверх» это `DY = -1`.
- Единицы: пиксели логического экрана (320x240 при мире 20x15), окно масштабирует.
- Тесты: табличные, `package <имя>` рядом с кодом. Каждый новый тест проверяем **мутациями** (намеренно ломаем код в копии репозитория в scratchpad и смотрим, краснеет ли тест). В каждом случае таблицы на границы нарушается ровно одно условие.
- Сравнение `float64` в тестах: с допуском (`math.Abs(a-b) < 1e-9`). Сейчас в `command_test.go` ещё `!=`, это хрупко, автору рекомендовано поправить.
- Стиль: `gofmt -s`, `go vet`, доккомментарии к экспортируемым именам начинаются с имени. Комментарии на русском.
- Git: ветка на задачу (`git switch -c <имя>`), потом слияние в `main` и `git push`. Сообщения коммитов на русском, описательные («Исправления» считается слишком общим). Claude **не выполняет git-операции за автора**, пока тот не попросит.

## 8. Известные недочёты и заметки по оптимизации

- `DrawGrid` перебирает **все** клетки каждый кадр. Когда мир вырастет и появится камера, рисовать только видимый диапазон клеток.
- `getRandomTile` использует глобальный `math/rand`: мир недетерминирован. По принципу проекта нужен свой генератор с seed (`rand.New(...)`), когда дойдём до генерации.
- `tileColors` — массив: у пропущенного индекса в середине будет прозрачный цвет, у отсутствующего в конце паника. Возможный тест: для каждого `TileType` есть цвет.
- `NewGrid` с отрицательными размерами паникует в `make`.
- У `TileType` нет метода `String()` (в сообщениях тестов печатается число).
- `float64` в позиции: нормально для сервера-арбитра; для lockstep-синхронизации на разных архитектурах могут расходиться результаты, тогда рассмотреть фиксированную точку.
- В `command_test.go`: сравнение через `!=`, нет `t.Run`/имён случаев в сообщениях, нет теста «расстояние шага равно Speed» для диагоналей.
- Имя игрока "test" и id=1 зашиты в `main` (заглушка).
